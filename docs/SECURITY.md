# Safety and access

## Identity and community scope

The local installation supports persistent server accounts without external credentials. Passwords use salted asynchronous scrypt, session/recovery tokens are stored hashed, and session cookies are HttpOnly/SameSite. Recovery revokes existing sessions and rotates the key. Auth attempts are limited. SQLite transactions and checked domain operations enforce account/community separation. Local accounts claim no email verification or delivery, and are disabled on Vercel or when Supabase is configured. The first adult local account bootstraps installation administration. [Account boundaries](ACCOUNTS.md).

Supabase Auth owns passwords, verification and session tokens. The Next.js server uses `getUser()`, protected route checks, same-origin mutation checks, payload bounds and Zod validation. Database functions derive the actor from `auth.uid()` and load owners and roles themselves. Supplying another user ID cannot accept that user's invitation. There is no service-role client, unrestricted messaging, payment collection or public student-profile endpoint.

Adult accounts can discover approved public adult communities and activities. Youth accounts can only access approved, moderated private hubs in which their membership is approved. A one-time self-declared age category is collected during onboarding; changing an established category requires an administrator process. New accounts default to youth and undiscoverable before onboarding. Self-declaration is not reliable age verification: a real youth rollout needs school identity checks, age assurance and active moderation.

Private hub contents are unavailable to nonmembers. The school picker exposes only approved school metadata (name, city and kind). Choosing a school creates a pending request and stores an affiliation; membership approval remains separate. A random 96-bit, single-use invite code is stored only as a SHA-256 hash and expires after seven days. Redeeming it also creates a membership request, not access. A verified hub administrator approves the member. Only a platform administrator can approve a hub as a school space. Hub creators cannot self-approve youth access. Peer tutors need approval inside the particular private hub; an expertise string is not a verification badge. Private managed rooms, venues, facilitators and projectors require hub-admin approval unless offered by the hub administrator.

School/community messages require current approved membership. Reciprocal adult connections enable private chats; youth connections require a shared approved private youth community and cannot open direct messages. Both-sided blocks and membership removal revoke reads and sends. Message authors come from server identity. Authors and group organizers can soft-remove messages. Direct writes to connection/message tables are revoked. Messages have a 1,500-character bound and a six-per-ten-second sender limit; friend requests have a daily bound. PostgreSQL serializes concurrent message sends for each sender before checking the limit. Polling updates every five seconds while visible, rather than claiming a push/realtime service.

Provider calendars are third-party content opened only on demand. AFA's allowlisted HTTPS venue pages can be framed; other operators use external links. Bookings and payments remain with the provider. Organizer-recorded booking references are kept in an owner-readable table and are excluded from shared API projections and calendar files. No provider credentials, confirmation scraping or payment collection are implemented in AfterBell.

Roles are stored in dedicated database tables. Hub creators become hub administrators; accepted users are members. The schema also supports organizer roles. Administrators can assign community roles through checked operations; organizers can review membership and issue invitations but cannot promote themselves. Owner transfer, last-administrator and confirmed-commitment checks protect continuity. No user can change their own role through an unverified profile payload.

## Mutation protection

Every application table has RLS. Authenticated direct table writes are revoked; all mutations use checked RPC operations. Security-definer helpers have pinned search paths and read only known tables. Client creation of public-schema objects is revoked. Anonymous execution is revoked. The read model uses invoker rights and retains RLS; narrow helpers supply counts or relevant busy intervals without returning another person's event details.

`afterbell_mutate` treats a direct RPC caller as untrusted, even if the Next.js API normally validates first. Database constraints protect enums, counts, dates, public city coverage, dependency shapes and ownership. Computed proposal actions use canonical offer owners, kinds, costs and quantities. A database feasibility check prevents a caller from marking an empty/invalid bundle feasible. Confirmation locks rows, checks the combination again, and relies on exclusion constraints for concurrent allocation races.

Proposals do not reserve resources. Invitations do not constitute acceptance. Only the invited participant or resource owner can respond. Every action must be accepted before the organizer confirms. A person's duplicate offers cannot count as multiple people. Shared resource dependencies are summed, so one unit cannot satisfy multiple missing requirements. Reservations cover both resources and people. Withdrawal or cancellation releases reservations; a replacement must be proposed and accepted.

Blocks are private and enforced in both directions in database discovery/matching predicates. Declines persist per activity and are excluded from later proposals. Reports are visible only to the reporter, platform administrators and authorized hub moderators; moderation actions are audit logged. Report text is rendered as React text, not executable HTML.

## Privacy

Only supported broad city and area reference IDs can be stored in location fields. User email remains in Supabase Auth and is not returned in community data. Student personal information is not exposed publicly. Group members are minimized/anonymized in the UI. The nearby directory is an explicit, separate adult opt-in and returns only first name and the agreed public fields; the private profile table remains own-row readable. Both-sided blocks and adult/onboarding eligibility are checked in the database. Device coordinates remain temporary browser memory and never enter API requests, storage or map URLs. See [nearby privacy and validation](NEARBY.md). Resource labels and public intros should not contain private contact details. The profile/data export contains only data authorized for the caller.

The demo contains no real people. Its cookie selects isolated local fixtures and does not authorize a live API. Simulator controls explicitly identify that they act for fictional characters. Browser storage is appropriate for this isolated fictional demo, not for secure multiuser records.

## Operational work before rollout

Configure and test the actual Supabase project, SMTP, redirect allowlists and email-confirmation settings; run the migration against a staging project and review Supabase advisors. Establish organization verification, real moderators, retention/deletion procedures, escalation and abuse handling. Add application-level rate limits, monitoring, pagination, load tests and an external security review before a large or youth-facing launch. Automated database and browser tests cover the implemented rules; they do not prove every deployment or operational process secure.
